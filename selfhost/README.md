# selfhost：让"同步上游"变成照单办事

## 为什么需要这一层

本仓库和上游 `sgangss/Stronghold-Protocol` **没有 git 共同祖先**（共同提交 0 个，`git merge-base` 退出码 1）。
所以：

- `git merge` / `git rebase` / GitHub 网页的 **"Sync fork" 全部不可用**；
- `git rev-list --count HEAD..upstream/master` 得到的 "落后 N 提交" 是**假数字** —— 没有共同祖先时它等于上游的全部历史，不是待补的增量；
- 想靠"找合并基线"来同步也不行：我们与上游最接近的版本仍差 1 万余行。

能同步的事实依据只有一个：**双方的实际差异很小且可枚举**。这份清单就是那个枚举。

## 三类文件

| 分类 | 含义 | 同步时怎么办 |
|---|---|---|
| `owner` | 上游**没有**的文件 —— 自托管层、我们的测试、我们加的客户端模块 | 直接整体复制过去，不需要判断 |
| `patched` | 上游**有**、但我们改过的文件 | 把我们的改动重新应用到上游的新版本上 |
| `hotspots` | `patched` 里**实测会冲突**的那几个 | 同步时唯一需要动脑的部分 |

**分工背景**：上游是纯游戏项目（浏览器端 + Node 服务器 + Dockerfile，**没有 `worker/`**）；本仓库 = 上游游戏 + Cloudflare Workers 自托管层。

## 实测：同步一次要动多少东西（2026-10-04）

用快照 `056a1ca` 当基线，对上游 `master` 跑了一次完整的三方合并：

| | 数量 | 说明 |
|---|---|---|
| `owner` 复制 | **52 个** | 机器操作，无需判断 |
| `patched` 自动合并 | **11 个** | 我们的改动干净地落在上游新版本上 |
| `patched` 需人工 | **3 个** | `package.json`(1 处)、`public/js/screens/room.js`(1 处)、`public/js/screens/title.js`(2 处) |

也就是说：**同步上游的人工成本 = 解 4 个冲突块**。另外注意 `server/match/Match.js` 和 `shared/protocol.js` 虽然上游也在改（37 行 / 28 行），但改动区域与我们的不重叠，**仍能自动合并** —— "上游改过"不等于"会冲突"。

## 为什么不把自托管层挪进一个目录

看起来更"整齐"的做法是把 `worker/`、`wrangler.jsonc` 等挪进 `selfhost/`。**不做**，因为：

- `worker/` 里的代码按相对路径 import 上游的 `../server/*`、`../shared/*`，挪一层就要把所有 import 路径改掉，是一次有风险的大改，而收益只是好看；
- `patched` 的 14 个文件**必须留在原位**（它们就是上游文件），所以"位置"根本表达不了"是不是我们的"；
- 真正需要的是**可校验的边界**，而不是目录形状 —— 这就是 `manifest.json` 存在的理由。

## 日常：改完代码要过门禁

```bash
npm run selfhost:check
```

它会重算边界并报错，当：

- 你改了文件但没在清单里分类（同步时会静默漏掉）；
- `owner` 里某个文件上游**现在也有了**（说明它不再是纯我们所有，得改判为 `patched`）；
- `patched` 里某个文件**上游删掉了**。

顺手它还会打印每个 `hotspot` 上游最近一次改动，让你知道冲突面有没有变化。

## 同步上游

```bash
npm run selfhost:sync -- v0.1.2 --fetch        # 目标可以是 tag，也可以写 upstream/master
```

脚本会：

1. 把目标版本导出到一个临时目录（默认 `%TEMP%/sp-sync/<ref>`），**不碰本仓库的工作区**；
2. 把 `owner` 的文件整体复制进去（含 `replay-versions/*.gz` 这类二进制）；
3. 对 `patched` 的每个文件做**三方合并**：ours=我们的版本、base=我们的快照提交、theirs=上游版本。
   - 上游**从没改过**该文件时，base 与 theirs 相同 → 我们的改动**自动干净应用**（14 个里有 9 个属于这种情况）；
   - 上游也改过时 → 产生冲突，脚本把带 `ours/base/theirs` 三方标记的结果写成 `<文件>.conflict` 给你手工处理。
4. 打印结果与冲突清单。

### 处理完冲突之后

1. 在导出的目录里构建、跑测试。
2. **确认 `RULES_VERSION` 变了**（上游动过 `server/`、`shared/`、`data/`，所以必然变）→ 规则版本变了以后，**进行中的对局无法恢复**，所以部署必须挑没有对局在进行的时候。用 DO 请求速率确认，或先把站点切到维护态。
3. 对照 `selfhost/manifest.json` 复查：有没有新文件该进 `owner`；有没有上游新增的同名文件该从 `owner` 改判成 `patched`。这一步**只能靠人** —— 没有共同历史，没有任何工具能替你判断。

## 不要做的事

- **不要试图 `git merge upstream/master`**，它会把两条无关历史搅在一起，产生成百上千个假冲突。
- **不要同步上游的 `test/`（100+ 文件）和 `tools/`（12 个文件）**，除非你真的需要：它们与自托管层无关，只会让每次同步都要重新解一堆冲突，而我们的 CI 是关的、本机 miniflare 全量套件也跑不完。
- **不要把 `dist/`、`.cache/`、`node_modules/` 混进清单** —— 那是构建产物。
